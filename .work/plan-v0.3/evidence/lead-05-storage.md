# lead-05 · Durable-состояние MyWork: миграции, journal, атомарность, рост БД

Вопрос: как устроено durable-состояние сегодня и что нужно для (а) единого реестра миграций, (б) атомарной записи + journal, (в) ограничителей роста. Работа только на чтение; живой профиль не изменялся, `*.sqlite` не создавались.

## Факты

1. **Где лежит состояние.** `packages/storage/src/layout.ts:24,27` (`dsh-mywork/state`), `:33-36` две БД — `registry|controller`, `:76-84` precedence explicit → `$DSH_HOME` → `~/.dsh`, `:91-93` `<stateDir>/<db>.sqlite`. Проверка: `pwsh` → `DSH_HOME=C:\Users\Dmitry\.dsh`, `Test-Path $DSH_HOME\dsh-mywork` → **False** (exit 0), т.е. живой БД нет. `scripts/verify-profile.mjs:129-133` хеширует только `~/.dsh/profiles/web/{package.json,cordis.patch.yml}` и `settings.yaml`, `:156` запускает DSH с изолированным `DSH_HOME` — состояние MyWork в реальный профиль не попадает.

6. **Journal и атомарность миграций уже есть.** `migrations.ts:97-103` DDL `schema_migrations(version PK, name, applied_at) STRICT`; `:142-184` `runMigrations` — отказ при `applied > latest` (`:150-156`), по одной транзакции на миграцию с перечитыванием `user_version` под write-lock (`:160-173`), строка журнала и `PRAGMA user_version` в той же транзакции (`:165-171`), журнал читается наружу `store.ts:135-138`/`:190-197`. В evidence-DDL прямо предполагается `recursive_triggers = 0` (`evidence/src/schema.ts:105`) — этот pragma не выставляется и не проверяется.
8. **Write-пути.** Всё durable-состояние — один SQLite-файл. Единственные не-SQLite записи в `packages`: временный `plan.json` для `bd create --graph` (`beads-adapter/src/adapter.ts:1051-1058`, снимается `:1067`) и внешний `bd kv set` для памяти (`beads-adapter/src/memory.ts:433`). `writeFileAtomic`/`withFileLock`/temp+rename/JSON-леджера в репозитории нет (0 совпадений).
9. **Рост.** 16 таблиц: storage 3 (`migrations.ts:54,72,98`), evidence 2 (`schema.ts:47,75`), lease 1 (`:48`), planner 6 (`schema.ts:60,66,87,100,112,130`), execution 4 (`schema.ts:88,111,120,139`). Растут неограниченно: `outbox` (`payload TEXT NOT NULL`, доставленные строки не удаляются — API только `append/markDelivered/markFailed`, `storage/src/outbox.ts:73-87`), `inbox_dedup` (только INSERT, `storage/src/inbox.ts:64-69`), `audit_events` (append-only), `artifacts` (`bytes BLOB NOT NULL`, `evidence/src/schema.ts:60`).
10. **Что мешает чистке.** Триггеры: `evidence/src/schema.ts:65-73` (artifacts UPDATE/DELETE), `:92-100` (audit UPDATE/DELETE), `:115-126` (BEFORE INSERT REPLACE-guards). Retention-окон, `prune`, TTL в коде нет.

## Опровержения/неожиданное

- **«Нет journal миграций» (D-6, `01-MASTER-PLAN.md:65-66`) в этой формулировке ложно:** `schema_migrations` + одна транзакция на миграцию + `user_version` существуют и покрыты четырьмя тестами (см. п.6). Реально отсутствуют: канонический реестр, `MIGRATIONS_REQUIRED`, verify-шаг и backup/rollback (MW-040).
- **«temp+rename / `withFileLock`» (`01-MASTER-PLAN.md:146`) не имеет адресата в собственном состоянии MyWork:** состояние — один SQLite-файл; единственная локальная файловая запись — эфемерный plan.json для `bd`. Пункт нужно либо снять, либо привязать к новому производному файлу.
- **Дефолтный список миграций не «неполный», а опасный в обе стороны:** помечает свежий файл как полную схему v1 и отказывает (`schema-version-unsupported`) открыть здоровую v6-БД.
- **Ретенция `outbox`/`inbox_dedup` не требует миграции схемы:** триггеров против DELETE у них нет; нужен код + окно. Наоборот, `artifacts`/`audit_events` требуют условного правила (v7), иначе DELETE невозможен в принципе.
- **Единый реестр в `packages/storage` заблокирован существующим тестом:** `tests/boundaries.test.mjs:223-224` запрещает `packages/storage/src/**` импортировать что-либо `@dsh-mywork/*` кроме contracts, а `:228-229` фиксирует `storage.devDependencies` ровно как `['@dsh-mywork/contracts']`. При этом четыре владельца списков сами зависят от storage (`packages/{evidence,lease,execution,planner}/package.json`), а `packages/controller/package.json:33-38` сегодня не зависит ни от одного из пяти. Направление реестра — только «вверх»: новый composition-пакет (или controller + 5 зависимостей), а не storage.
- **Store не открывается ни одним продакшн-процессом**, поэтому живого `$DSH_HOME\dsh-mywork` нет и рост/`VACUUM` сегодня ненаблюдаемы.

## Не проверено

- Действующий уровень `PRAGMA synchronous` (дефолт SQLite) — не выставляется и нигде не проверяется; своих БД я не открывал (запрет на создание `*.sqlite`). Это `Шаг 0` для F-35.
- Реальные темпы роста и поведение `VACUUM`/checkpoint, а также пишет ли что-нибудь в `artifacts.bytes` вообще (потребителя нет — store ещё не подключён).
- Как boundary/reachability-тесты отнесутся к **новому** composition-пакету (его правил в `tests/boundaries.test.mjs` нет) и не сломает ли добавление 5 зависимостей в `controller`.
- Ограничители роста у Beads/Dolt (`.beads/embeddeddolt`) — вне MyWork DB, не читал.

## Что это значит для плана

1. **F-18:** реестр `MYWORK_DATABASE_MIGRATIONS` (v1…v6) собирается в **новом** composition-пакете (или controller), а не в `packages/storage/src/migrations.ts`, как записано в `30-CARD-EDITS.md:873` — иначе красный `tests/boundaries.test.mjs:223-229`; storage оставляет только kernel-список.
2. **F-19:** `migrations` становится обязательным (`store.ts:68-69,84`), отказ кодом `MIGRATIONS_REQUIRED`; тест обязан покрыть обе стороны дефекта (свежий файл → не v1-«полный»; v6-файл → не `schema-version-unsupported`).
3. **F-20:** journal расширяется verify-шагом в `runMigrations` (`migrations.ts:142-184`); существующую транзакционность и отказ «новее, чем билд» сохранять, не переписывать.
4. **F-33/34/35:** файловой атомарности делать нечего — работа в том, чтобы зафиксировать `synchronous`, политику WAL-сайдкаров/checkpoint и убить неверный дефолт; temp+rename/`withFileLock` не применять без нового носителя.
5. **F-38/39/40:** `outbox`/`inbox_dedup` — API удаления + окно (миграция не нужна); `artifacts`/`audit_events` — условное правило v7 поверх `evidence/src/schema.ts:65-73,92-100,115-126` плюс `VACUUM`/checkpoint, которых сегодня нет вовсе.
6. **`MYWORK_SCHEMA_VERSION`** перестаёт быть константой 1: либо считается от собранного реестра (→6), либо удаляется вместе с правкой `tests/storage-crash.test.mjs:70`.
