## 1. Пробы

### 1.1 Негативная проба: вызовов git в исходниках пакетов нет

Команда (регулярка, **без** `-SimpleMatch`):

```
(Get-ChildItem -Recurse packages -Filter *.ts -File | Where-Object { $_.FullName -notmatch '\\lib\\' } | Select-String -Pattern 'execFile|spawnSync|rev-parse|worktree add').Count
```

Результат: `9` — **не** `0`, как в замере плана от 2026-09-27. Разбор совпадений: все девять лежат в
`packages/gate-runner/src/runner.ts` (`:26`, `:70-75`, `:414`, `:428`, `:479`, `:489`) — пакет создан
другим шагом кампании уже после замера плана. То есть посылка «git-процессов в `packages` нет вообще»
на дату шага неверна, но посылка, которая нужна решению, проверяется отдельно:

```
(Get-ChildItem -Recurse packages\execution -Filter *.ts -File | Where-Object { $_.FullName -notmatch '\\lib\\' } | Select-String -Pattern 'execFile|spawnSync|rev-parse|worktree add').Count
```

Результат: `0` — исполнителя изоляции в слое саги нет, и запускать процесс он не умеет.

### 1.2 Позитивный контроль

```
(Select-String -Path tests\beads-adapter.test.mjs -Pattern 'execFile|spawnSync|rev-parse|worktree add').Count
```

Результат: `2` (план ожидал `3`; файл изменился после замера плана, строки сместились) — совпадения на

регулярка находит совпадения там, где они есть. Разница с планом зафиксирована, а не спрятана.

### 1.3 Жёсткое ограничение сборки слоя саги

```
Select-String -Path tests/boundaries.test.mjs -Pattern "deepEqual\(modules, \['node:crypto'\]"
```

Результат: совпадение на `tests/boundaries.test.mjs:564` (план называл `:488`; файл вырос, строка
сместилась, смысл тот же):

> `assert.deepEqual(modules, ['node:crypto'], ...)` — собранный бандл `packages/execution/lib/index.js`
> может импортировать ровно один внешний модуль, `node:crypto`.

Вывод, который отсюда следует и определяет место раннера: процесс, говорящий с `git`, **не может** жить
в `packages/execution` — иначе этот тест краснеет. Он живёт в отдельном пакете-адаптере, а слой саги
зависит только от порта (тип) и от словаря отказов (значение, инлайнится в бандл).

## 2. Решения

1. Порт: `WorktreePort` в `packages/contracts/src/worktree.ts:201` (создан на этом шаге Lead'ом,
   не переписывается) — `prepare`, `resolve`, `cleanup`, `list`, каждый метод отвечает `Result<…>`,
   отказы закрыты шестью значениями `WorktreeRefusal`.
2. Реализация: новый пакет `packages/worktree-adapter` — единственное место в дереве, где изоляция
   запускает `git`; он реализует и `GitPort` (`packages/contracts/src/git.ts`), и порт изоляции.
   `pnpm-workspace.yaml` (`packages/*`) подхватывает пакет без правки файла.
3. Политика: попытка работает только внутри своего worktree — общий `shared checkout` воркспейса не
   трогает ни один метод порта, `prepare` режет ветку от зафиксированного `baseSha`, а `cleanup`
   отказывается удалять грязное и чужое.
4. Форма `Attempt.worktree` не расширяется: остаётся `readonly worktree?: WorktreeRef`
   (`packages/contracts/src/attempt.ts:122`). Факт привязки (путь, ветка, `base_sha` до работы,
   `head_sha` после) получает отдельная таблица `attempt_worktree` — шаг E-04.
5. Пустой репозиторий — явный отказ `EMPTY_REPOSITORY` из `prepare`, без скрытого первого коммита:
   `git rev-parse --verify HEAD` читается до создания ветки, и отсутствие коммита не «лечится» коммитом
   от имени вызывающего.
6. Значение по умолчанию для `retentionMs` до `D17`: `7 * 24 * 3600 * 1000` (7 суток), пометка
   «значение по умолчанию до `D17`» — из шага E-06, политику задаёт вызывающий.

## 3. Риск, который надо назвать явно

Решение принято **до** расширения сканера границ (`FINAL-REPORT` §10, этап 2, п. 8). Новый пакет обязан
попасть в список сканируемых пакетов вместе с остальными: пока он вне списка, его собственные
зависимости (`node:child_process`, `node:fs`) не проверяются ни одним гейтом — это свойство сканера, а
не разрешение тянуть что угодно. Ровно поэтому раннер и вынесен из слоя саги: у `packages/execution`
граница уже есть и она жёсткая (§1.3).
