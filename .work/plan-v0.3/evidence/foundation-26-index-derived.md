## `lastSyncedRevision`: порядок разрешения и почему штамп — метаданные

`--revision` → иначе ревизия Host-леджера (если файл читается) → иначе `planRevision` из `tasks.json`.

`--check` сравнивает **тело таблиц**, а расхождение штампа печатает отдельной строкой-замечанием, не падая. Причина прямая: на чистой машине без Host-леджера (CI, свежий клон) штамп неизбежно будет другим, и «индекс сломан» было бы ложной диагностикой. Проверяемое содержимое — таблицы; штамп говорит, когда они собраны.

## Дефект, найденный и исправленный по ходу

Первый вариант миграции вставлял **двойной** перевод строки перед маркером, тогда как устойчивый путь — одинарный. Из-за этого файл сходился только со **второго** прогона (`run1` переписывал, `run2` — уже нет). Исправлено на одну каноническую форму для обоих путей; после правки проверено: миграция из немаркированного файла даёт фиксированную точку **за один прогон** (`hash_equal_after_one_migration = True`).

## Ограничения

- `phaseOrder` сортирует лексикографически. Если появится этап с именем, которое должно стоять не по алфавиту, порядок придётся задавать явно — сейчас это совпадает с прежней рукописной раскладкой.
- Тесты работают на фикстуре из 3 карточек, а не на реальном `tasks.json`: реальные 55 строк проверены гейтом `--check`, а не тестом.
- Генератор пишет файл целиком через `writeFileSync`, без блокировки. Параллельный запуск двух генераторов может дать гонку.

## Что НЕ проверено

- Не проверено, как `--check` поведёт себя, если `tasks.json` недоступен или повреждён (парсинг упадёт исключением, а не внятным сообщением).
- Не проверялось, что кто-то другой не правит таблицы руками: следующая правка внутри маркеров будет молча затёрта при пересборке — это задумано, но не защищено ничем, кроме комментария в шапке скрипта.
- Не проверено поведение на CRLF-файле: генератор пишет LF, поэтому первая пересборка нормализует переводы строк во всём файле.
