# ADR-032. Peer/version policy и способ распространения MyWork

- **Статус:** проект (требует утверждения владельца)
- **Дата:** 2026-09-26
- **Решает:** владелец (рекомендация — `decision-desk`, решение D04, конфликт K10)

## Контекст

Платформа ввела обязательную проверку совместимости: несовместимые peer-зависимости **блокируют установку и активацию**, а исключение выдаётся только человеком и только на точную пару «пакет@версия ↔ версия DSH».

MyWork сегодня этой проверке **не подвергается**, и причина видна построчно:

- гейт пропускает всё, что не начинается с `@deepseek-ai/dsh-`: `if (name !== '@deepseek-ai/dsh' && !name.startsWith('@deepseek-ai/dsh-')) continue` (`packages\boot\app-boot\src\plugin-compatibility.ts:75`);
- единственный peer во всём репозитории — `{"@deepseek-ai/cordis": "^4.0.2"}` (`packages\controller\package.json:30-32`) — под условие **не подпадает**;
- при пустом наборе гейт возвращает `undefined`: `if (Object.keys(peers).length === 0) return undefined` (`:81`);
- и вовсе не смотрит манифест без `peerDependencies`: `if (!Object.hasOwn(fields, 'peerDependencies')) return undefined` (`:68`).

Итог: проверки нет, и «установка проходит» означает ровно «гейт слеп».

Одновременно распространение невозможно штатным путём: все 12 пакетов — `private: true`, а `scripts\pack.mjs:20,34` пакует **только** `packages/controller`, `files` которого — `["lib", "cordis.patch.yml"]` (`packages\controller\package.json:17-20`) при `workspace:*`-зависимостях на непубликуемые `@dsh-mywork/*` (`:35-37`).

## Решение

1. **Объявить peer по пакету платформы, а не по сервисам.** Гейт читает **имена пакетов**, поэтому в `packages\controller\package.json` добавляется:
   `"@deepseek-ai/dsh": ">=0.1.7-rc.2 <0.3.0-0"` — рядом с существующим `"@deepseek-ai/cordis": "^4.0.2"` *(дельта 2026-10-03: было `>=0.1.7-rc.2 <0.2.0`; см. «Дополнение 2026-10-03» §3).*
   Имена сервисов остаются в `inject`-списке Cordis и к гейту отношения не имеют.
2. **Добавить `dsh.engines.dsh` как декларацию.** *(Исправлено 2026-10-03: здесь стояло «Гейт его не читает, но читают издатели и **Plugin Manager**» — читателей нет ни в коде, ни в Plugin Manager: тип объявлен `packages/util/package-manifest/src/types.ts:24,56-66`, а `packages/boot/app-boot/README.md:52` прямо говорит «These checks use peer declarations, not `engines.dsh`».)* Поле остаётся подсказкой человеку и издателю: `"dsh": { "engines": { "dsh": ">=0.1.7-rc.2 <0.3.0-0" }, "bundle": { "patch": "./cordis.patch.yml" } }` (`bundle.patch` уже есть, `packages\controller\package.json:21-25`). Гейт включает **только** `peerDependencies` (п.1); диапазон в `engines` держится тем же для согласованности, но сам не включает ничего.
3. **Сохранить `engines.node`** корня (`package.json:9-11`, `>=22.18.0`): платформа его не читает, издатели и CI — читают.
4. **Распространять tarball'ом.** Единственный канал — `pnpm run pack:local` → `scripts\pack.mjs`, а проверка установки — `scripts/verify-profile.mjs`.
5. **`private: true` сохранить у всех 12 пакетов.** Снятие — только у будущего `@dsh-mywork/web` и только если он пойдёт в реестр; это отдельное решение, не следствие этого ADR.
6. **Исключения версий не выдавать.** Если гейт отказывает — обновлять MyWork или платформу, а не выдавать exemption: exemption рискует крахом и потерей данных, и это записано в самом тексте предупреждения платформы.

## Отклонённые альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| **Оставить как есть** | «Установка проходит» означает «гейт слеп»: при несовместимом обновлении DSH плагин смонтируется и упадёт в рантайме вместо явного отказа на установке |
| **Опубликовать `@dsh-mywork/controller` в реестр** | Требует снятия `private` при `workspace:*` на непубликуемые пакеты; публиковать 12 пакетов ради одного пользователя — 12 необратимых имён. `docs\cookbook\adding-a-package.md:27` требует зеркалировать каждый dsh-peer в `devDependencies` и держать stateless-утилиты в `dependencies` |
| **Vendored: положить исходники в профиль без манифеста** | Гейт снова молчит (`plugin-compatibility.ts:68`), а `docs\user\develop\basic\publish.md:105` прямо снимает с resolution ответственность за проверку ranges |
| **Полагаться на `dsh.engines.dsh` вместо peers** | Гейт читает **только** `peerDependencies`: `evaluatePluginCompatibility` обращается к `fields.peerDependencies` и ни к чему больше |

## Последствия

**Код.** Правка `packages\controller\package.json`. `scripts\pack.mjs` становится не «одним из», а единственным каналом доставки; шаг установки обязан проверять, что tarball **ставится**, а не только собирается.

**Контракты.** Ни один доменный контракт не меняется.

**Карточки.** MW-040 (состояние MyWork) дополняется пунктом «гейт не молчит»; MW-048 (UI-пакет) — снятие `private` только у web-пакета и только при публикации.

**Что перестаёт быть верным.** (а) «MyWork нельзя установить, потому что все пакеты `private`» — tarball-path снимает это без публикации; (б) `FINAL-REPORT §3.3(1)` в части «`peerDependencies` по реально используемым сервисам» — гейт читает имена **пакетов**, поэтому peer объявляется по `@deepseek-ai/dsh`, а сервисы остаются в `inject`.

## Проверка (как доказать, что решение работает)

Целевой гейт — вызов гейта на нашем манифесте: при совпадающей версии DSH он возвращает `undefined` **потому, что диапазон satisfiable**, а не потому, что поля нет; при заведомо несовместимом диапазоне — объект с непустым `peers`. Различие между «молчит по делу» и «молчит от слепоты» проверяется подменой диапазона на `999.0.0` — образец ожидания есть в `apps\cli\tests\plugin-compatibility.expected.e2e.ts:24-25,54-61`.

## Условия пересмотра

1. Появится второй потребитель MyWork — тогда реестр или git-URL.
2. DSH изменит форму проверки (например, начнёт читать `dsh.engines` вместо peers).
3. Плагин понадобится ставить через UI Plugin Manager — tarball перестанет быть достаточным.
4. **(добавлено 2026-10-03)** Выйдет `0.2.0` final: выбранный диапазон `>=0.1.7-rc.2 <0.3.0-0` его принимает, а при возврате к `<0.2.0` строка плагина станет `disabled` (`packages/boot/app-boot/src/compatibility-preflight.ts:79-83`) / бандл уйдёт в `skippedBundles` (`src/profile.ts:675`) — это записанный отказ, а не сюрприз. Проверка — арифметика semver и подстановка `0.2.0` в настоящую функцию гейта (см. «Дополнение 2026-10-03» §2).

## Канон и отменённые формулировки

**Канон (этот ADR):** peer объявляется **по имени пакета платформы** — `@deepseek-ai/dsh` в `peerDependencies`; имена сервисов Cordis к гейту отношения не имеют и остаются только в `inject`-списке плагина.

**Отменено:**

| Где | Формулировка | Статус |
|---|---|---|
| `22-STEPS-surface.md`, шаг `B-18` п. 3 | «peer по сервисам» | **Отменена.** Противоречит `plugin-compatibility.ts:75`: гейт перебирает **имена пакетов** и пропускает всё, что не начинается с `@deepseek-ai/dsh-`; имя сервиса в `peerDependencies` не даст ничего, имя пакета — даст |
| `10-DECISIONS.md`, D04, первая редакция выбора | «peers по реально используемым сервисам» | **Отменена** там же (исправлено); канон — этот ADR |
| `20-STEPS-foundation.md`, шаг `F-48` | уже исправлено на peer по пакету | **Согласовано** с этим ADR |
| `00-RECON.md` §3.3 п.1 | «читает **только** `peerDependencies` имён `@deepseek-ai/dsh`/`@deepseek-ai/dsh-*`… Диапазон плана — **`>=0.1.7-rc.2 <0.3.0-0`** (решение владельца 2026-10-03; прежний `<0.2.0` отвергал бы `0.2.0` final)» | **Согласовано** с этим ADR: прежняя формулировка §3.3 п.1 («`peerDependencies` по реально используемым сервисам» + диапазон `<0.2.0`) **снята** правкой 2026-10-03; канон — этот ADR |

**Почему это не стилистика.** `evaluatePluginCompatibility` (`packages/boot/app-boot/src/plugin-compatibility.ts:71-80`) обходит `Object.entries(fields.peerDependencies)` и на строке `:75` пропускает всё, кроме `@deepseek-ai/dsh` и `@deepseek-ai/dsh-*`. Сервисное имя (`webServer`, `typertGateway`, …) не совпадёт ни с одним из двух условий и будет **молча пропущено** — то есть peer «по сервисам» не включит гейт, а создаст видимость его наличия. Это худший из возможных исходов: проверка выглядит сделанной и не работает.

## Дополнение 2026-09-27 (исполнение F-48/F-50, этап 3)

**1. `dsh.engines.dsh` — документация, а не контракт.** Проверено исполнением: `engines` не читает **никто** в платформе (тип объявлен в `packages/util/package-manifest/src/types.ts`, но `rg engines` по `packages/**/*.ts` даёт только сам тип и его реэкспорт; `dsh?.engines|engines?.dsh` — 0 совпадений), и документация это подтверждает: «These checks use peer declarations, not `engines.dsh`» (`packages/boot/app-boot/README.md:52`). Контракт совместимости держит **исключительно `peerDependencies`**. Поле остаётся допустимым как подсказка человеку (`@dsh-mywork/web` его несёт — как и установленный эталон `@linxin666/dsh-client-ui-task-board@0.4.3` на 2026-09-27 — на 2026-10-03 в профиле 0.4.4), но включение гейта от него не зависит и в контроллере его нет.

**2. Носителями peer'а являются ровно два пакета, и это проверяется тестом.** `@dsh-mywork/controller` (читает платформенные сервисы через `ctx.*`) и `@dsh-mywork/web` (его браузерная половина `require`'ит `react` и store платформы, и его строку монтирует DSH). Множество зафиксировано `tests/peer-gate.test.mjs` по именам: третий декоративный носитель или молчаливая потеря peer'а у любого из двух роняет тест.

**3. Верхняя граница диапазона — решение владельца (D04, подтверждено 2026-09-27).** Замер: объявленный `>=0.1.7-rc.2 <0.2.0` принимает `0.1.7-rc.2`, `0.1.7`, `0.1.8`, `0.1.8-rc.1` и **`0.2.0-rc.1`** (пререлиз следующей линии), и отвергает `0.2.0`. Владелец оставил диапазон **как объявлено**, приняв остаток `0.2.0-rc.1`: любое ужесточение (`<0.2.0-0`) — только отдельным решением, а не «по ходу». Ловушка, снятая замером: `^0.1.7` десугарит в `>=0.1.7 <0.2.0-0` и **отвергает** текущий `0.1.7-rc.2`, то есть «эквивалент `^0.1.7`» — неверная характеристика объявленного диапазона.

## Дополнение 2026-10-03 (актуализация под DSH `0.2.0-rc.2`, checkout `639ed0153`)

**1. Почему объявленный диапазон «проходил» и где он ломается.** Гейт читает **только** `peerDependencies` имён `@deepseek-ai/dsh`/`@deepseek-ai/dsh-*` (`packages/boot/app-boot/src/plugin-compatibility.ts:68,75`) и сравнивает версию рантайма через `semver.satisfies(runtimeVersion, requirement, { includePrerelease: true })` (`:77` — пререлизы участвуют **всегда**); сама версия рантайма берётся из `package.json` пакета app-boot (`:44-49`) и сейчас равна `0.2.0-rc.2`. Значит `0.2.0-rc.2` попадает в `>=0.1.7-rc.2 <0.2.0` **не потому, что диапазон покрывает линию 0.2.x, а потому что пререлиз сортируется ниже своего релиза**. Это ровно тот остаточный риск, который был замерен 2026-09-27 для `0.2.0-rc.1` («Дополнение 2026-09-27» §3) и признан принятым: риск реализовался — владелец уже работает на `0.2.0-rc.2`, и гейт молчит без conformance. Первый же релиз линии (`0.2.0` final) этот диапазон **отвергает**: установка отклоняется (`packages/boot/plugin-manager/src/operations.ts:344,479`), на старте строка получает `disabled` / бандл уходит в `skippedBundles` (`compatibility-preflight.ts:79-83`; `src/profile.ts:675`).

**2. Замер (semver `7.8.5` — тот же, что импортирует гейт: `packages/boot/app-boot/node_modules/semver`; `includePrerelease: true`, как в `:77`).**

| Версия рантайма | `>=0.1.7-rc.2 <0.2.0` (было) | `>=0.1.7-rc.2 <0.3.0-0` (**выбрано**) | `>=0.2.0-rc.2 <0.3.0-0` (альтернатива) |
|---|---|---|---|
| `0.1.7-rc.2` | true | true | false |
| `0.2.0-rc.2` (текущая) | **true** (только из-за `includePrerelease`) | true | true |
| `0.2.0` (финал линии) | **false** | true | true |
| `0.2.1-alpha.1` (пререлиз внутри линии) | false | **true** | **true** |
| `0.3.0-rc.1` (пререлиз следующей линии) | false | **false** | **false** |

Замер воспроизведён и настоящей функцией гейта (импорт `packages/boot/app-boot/src/plugin-compatibility.ts`, рантайм подставлялся третьим аргументом): `undefined` при `0.1.7-rc.2`/`0.2.0-rc.1`/`0.2.0-rc.2`; объект отказа при `0.2.0` для старого диапазона; для выбранного диапазона — `undefined` при `0.2.0-rc.2`/`0.2.0`/`0.2.1-alpha.1` и отказ при `0.3.0-rc.1`.

Ловушки, снятые тем же замером: `<0.3.0` **без** `-0` пропускает `0.3.0-rc.1` (та же болезнь верхней границы, что у `<0.2.0`); `^0.2.0` (без `-rc`) десугарит в `>=0.2.0 <0.3.0-0` и **отвергает** текущий `0.2.0-rc.2`; `^0.2.0-rc.2` ≡ `>=0.2.0-rc.2 <0.3.0-0`. **Остаток, который выбранный диапазон не закрывает:** `-0` защищает границу **линии**, а не пререлизы **внутри** неё, поэтому `0.2.1-alpha.1` гейт пропускает (`true`). Если это неприемлемо, строгий вариант — `>=0.1.7-rc.2 <0.2.1-0` (проверено: `0.2.1-alpha.1` → отказ, `0.2.0` → принят); он **не** применяется без отдельного решения владельца.

**3. Новое значение — решение владельца 2026-10-03.** В `packages/controller/package.json` (peer) и `packages/web/package.json` (peer и `dsh.engines.dsh`) объявляется **`">=0.1.7-rc.2 <0.3.0-0"`**. Обоснование: нижняя граница — уже проверенная база (F-48 §8: tarball ставится и монтируется на `0.1.7-rc.2`), поэтому ни одна работающая сегодня конфигурация не отказывает; верхняя — граница линии с `-0`, которая впервые закрывает дефект верхней границы **по существу** (`0.3.0-rc.1` отвергается). **Альтернатива** `">=0.2.0-rc.2 <0.3.0-0"` (≡ `^0.2.0-rc.2`) зафиксирована как условие пересмотра: она применяется, если аудит покажет, что база 0.1.x больше не поддерживается, — тогда нижняя граница честно означает «на чём собрано», ценой отказа на `0.1.7-rc.2`.
