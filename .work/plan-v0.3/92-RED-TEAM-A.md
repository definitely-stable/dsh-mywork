## §3. Неисполнимые шаги (подробно)

### 3.1. Три шага на одну версию миграции `v7` — store не откроется

Дословно:

* F-36 (`20-…:952`): «канонический список миграций содержит миграцию **версии 7** с таблицей **`background_job`**»;
* F-40 (`20-…:1057`): «**новая миграция версии 7** (версия 7 **свободна** — проверено: `version: 7` в `packages/*/src/*.ts` и в `tests` → 0 совпадений)»;
* E-04 (`21-…:214,216,222`): «миграция `v7`», `CREATE TABLE attempt_worktree(...)`, «`PRAGMA user_version` (= 7)».

Все три живут в одном `controller.sqlite` (D09: «`controller.sqlite` — истина»; F-29: «тот же файл, тот же полный список миграций»). Валидатор (`packages/storage/src/migrations.ts:111-129`) бросает `StorageError('invalid-input', '… must be ordered by unique version, 7 follows 7')` — то есть **ни один store не откроется вообще**, а F-20 добавит к этому отказ `MIGRATION_JOURNAL_INCONSISTENT`. Дополнительно B-12 (`22-…:624`) объявляет `version: 2` для `board-projection`, а `version: 2` уже занята `EVIDENCE_MIGRATIONS[0]` (`packages/evidence/src/schema.ts:140`).

**Как есть:** исполнение F-36/F-37 и E-04 «параллельно» (они в разных файлах плана) даёт неработающую базу, а оба гейта при этом **зелёные** (тесты на `:memory:` с одним списком миграций).
**Переписка:** ввести в F-18 единственный источник номеров (`nextVersion()`/таблица «версия → таблица → шаг») и записать в гейт F-18 проверку «в каноническом реестре нет дублей и он равен сумме пяти списков»; F-36 → v7, F-40 → v8, E-04 → v9, E-19 → v10, E-28 → v11, E-34 → v12, E-37 → v13, B-12 → v14 (или привязывать board-таблицы к storage-списку с явной нумерацией). Тест F-18 не должен содержать литерал `[1,2,3,4,5,6]`.

### 3.2. Доска адресуется `MW-0NN`, а её идентификаторы — UUID

Проверено вызовом: `task_board_get MW-044` → `{"ok": false, "code": "task-not-found"}`. В `task_board_list` карточки имеют `id` вида `cc19da5a-ff24-45ed-8b19-236e02b2556d`, а `MW-002` — это **начало `title`**. От этого зависят F-06 (`task_board_get <id>`), F-07 (`task_board_manage { taskId: 'MW-027' }`), F-09 («для каждой: `task_board_get <id>`»), F-62 (пересчёт корпуса), F-61 (пиннинг `mode`).
**Как есть:** три шага этапа 0 (F-06, F-07, F-62) в написанном виде не выполняются ни одной командой.
**Переписка:** в каждый из них вставить Шаг 0 «`task_board_list {query: 'MW-027'}` → взять `id`», а в F-09 — команду, дающую сразу список (`task_board_list {includeArchived: true}` + фильтр по `latestExecution.result`).

### 3.3. `corepack pnpm <script>` не работает для корневых скриптов

Замер: `corepack pnpm --version` → `12.4.2`, `EXIT=0` (как в F-01). Но `corepack pnpm run typecheck` → `EXIT=1` за 1 с:

```
$ pnpm -r run typecheck
[ERROR] This project is configured to use 12.4.2 of pnpm. Your current pnpm is v11.7.0
```

Потому что корневой скрипт — `pnpm -r run typecheck`, а вложенный `pnpm` резолвится из PATH (DSH `.bin\pnpm` = 11.7.0) и падает на `pmOnFail` (`package.json:8` требует 12.4.2). Работает только `corepack pnpm -r run typecheck` → `EXIT=0`, 12 пакетов `Done`.
**Следствия:** неисполнимы гейт F-01 (шаг 4), гейт F-12 (команда 2), шаг 4 и гейт F-25, а также любая ссылка «`pnpm run check`» в файле 21 (§1.5 сам запрещает `pnpm run build/check` как гейт — это **прямое противоречие между файлами 20 и 21**, а не осторожность).
**Переписка:** всюду заменить `corepack pnpm run <script>` на `corepack pnpm -r run <script>` (или на `node_modules\.bin\tsc.cmd`, как это уже сделано в файле 21 — он проверен и работает).

### 3.4. F-17/F-21/F-22 требуют живого `bd`, которого «нет», хотя он есть — но не спавнится

`bd` установлен: `%APPDATA%\npm\bd.cmd` (334 б) → `node_modules\@beads\bd\bin\bd.js`; `bd.cmd version` → `bd version 1.3.0`. Но `spawnSync('bd', ['version'], {shell:false})` → **ENOENT**, потому что `bd` — `.cmd`-шим, а не PE-файл, и в проекте (`node_modules/.bin/bd`) его нет.
**Следствия:** (а) локально гейт F-17 (`skipped 0`) неисполним до F-13…F-16 — план это учитывает цепочкой зависимостей; (б) F-21 объявляет «сейчас FAIL», хотя сейчас **SKIP** — и «падающий тест» написать физически нельзя, пока тест не запускается; (в) F-22 гейт зелёный **до** работы.
**Переписка:** в F-21 первым шагом записать «снять доказательство SKIP (exit 0, 23 skipped), затем — падение после F-17»; в F-17 добавить предупреждение, что после F-13/F-14 23 теста начнут запускать реальный `bd` (создание Dolt-воркспейсов) в **обычном** `node --test`, а не только в CI (§5).

### 3.5. F-58/F-59/B-25: рукописный бандл удаляется сборкой; гейт требует живого профиля

Все 12 `packages/*/tsdown.config.ts` содержат `clean: true` (проверено поштучно). Шаг F-58 кладёт клиентскую половину **руками** в `packages/web/lib/client.js`, то есть в `outDir` пакета → первая же сборка `packages/web` (или `pnpm -r run build`) её стирает; гейт «панель видна в GUI после перезагрузки страницы» требует установки нового плагина в **живой профиль** — действие владельца.
**Переписка:** эмитить бандл конфигом (`packages/web/tsdown.client.ts`, как в B-25) с отдельным `outDir` вне `lib/`, либо `clean: false` для этого пакета с явным `entry`; гейт разделить на машинную часть (тест манифеста/бандла) и owner-gate «видно в GUI».

### 3.6. F-25: «зелёный прогон CI» и грязный lockfile
