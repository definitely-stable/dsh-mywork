## 1. Что строим (deliverable)

**План v0.3** — рабочий документ, по которому можно исполнять работу карточками, без дополнительных исследований. Требования владельца:

1. **План** — что делаем, в каком порядке, с какими гейтами, что НЕ делаем.
2. **Подробные последующие шаги реализации** — битсайз-шаги (2–5 минут каждый): точные пути файлов, что писать, какая команда, какой ожидаемый вывод, какой тест доказывает.
3. **Варианты там, где нужно решение** — максимально подробный разбор альтернатив (≥3 там, где они реально есть), критерии, доказательства, матрица сравнения, выбранный вариант и его последствия. Решение принимается в документе (рекомендация + условие пересмотра), а не откладывается.

Каталог: `.work/plan-v0.3/`. Владелец читает `README.md` → `01-MASTER-PLAN.md` → нужный файл шагов.

### 1.2. Формат шага (канон для 20/21/22/23)

Каждый шаг — атомарное действие с проверкой. Обязательные поля:

```markdown
#### F-07 · Единый список миграций: запретить открытие store без канонического набора
- **Карточка:** MW-059 (новая), зависит от F-03
- **Усилие:** S (30–60 мин) · **Риск:** низкий · **Откат:** revert коммита
- **Цель:** `openStore()` без явного списка миграций падает типизированной ошибкой.
- **Файлы:** Modify `packages/storage/src/migrations.ts:91-94`; Create `tests/storage/migrations-registry.test.mjs`
- **Шаги:**
  1. Тест (падающий): `openStore({ migrations: [] })` → ожидаем `MIGRATIONS_REQUIRED`.
     Команда: `node --test tests/storage/migrations-registry.test.mjs` → FAIL «MIGRATIONS_REQUIRED не брошен».
  2. Реализация: экспортировать `MYWORK_DATABASE_MIGRATIONS` … (код)
  3. Команда: `node --test tests/storage/migrations-registry.test.mjs` → `pass 1 / fail 0`.
  4. Регрессия: `node --test tests/**/*.test.mjs` → без новых падений.
- **Гейт (готово когда):** `<точная команда>` → `<точный ожидаемый вывод>`
- **Evidence в отчёт:** вывод команды, sha коммита, изменённые пути.
- **Риски:** …
```

Правила: один шаг = одно действие; никаких «и так далее»; все пути — от корня репозитория (`packages/...`, `tests/...`, `scripts/...`); номера строк указываются, только если проверены; если путь/строка не проверены — писать `~` и добавить в «Открытые проверки».

### 1.3. Формат решения (канон для 10-DECISIONS.md)

```markdown
## D02 · Модель зон доски (K2)
- **Кто решает:** владелец (рекомендация обязательна) · **Обратимость:** средняя (падают 8 тестов, приёмки MW-049/050, нужен ADR-018-bis)
- **Контекст:** 3–6 строк: что за выбор и почему он возник.
- **Критерии:** таблица «критерий · вес · как измеряем».
- **Варианты:** A/B/C — по каждому: суть, что даёт, чем платим, доказательства (`файл:строка`, `§`, команда+exit code), усилие, обратимость.
- **Матрица:** критерий × вариант (баллы 1–5) + итог.
- **Выбор:** вариант X. Почему он, а не остальные — 3–6 пунктов.
- **Условие пересмотра (триггер):** что должно произойти, чтобы решение отменили.
- **Последствия:** что меняется в коде/контрактах/карточках/ADR; что перестаёт быть верным.
- **ADR-действие:** новый ADR / правка ADR0NN / без ADR (почему).
- **Что осталось неизвестным:** списком.
```

Если решение требует эксперимента (spike), в решении описываются: гипотеза, что измеряем, бюджет времени, критерий «дороже бюджета → берём вариант B». Эксперимент **не выполняется** в этой кампании, если он мутирует живое дерево/профиль; описывается как шаг плана.

## 5. Правила доказательности и запреты

1. Утверждение без доказательства не считается: `файл:строка`, `§` отчёта, или команда + exit code. Для чисел — команда, которой число получено.
2. Не выдавать план за факт: если шаг зависит от непроверенного API, шаг начинается с проверки (`Шаг 0: подтвердить, что …`).
3. Не мутировать живое: никаких `pnpm install`, `pnpm build`, полного прогона тестов без нужды, никаких правок профиля/DSH-checkout/кода. Мутирующие эксперименты — только если Lead явно разрешил и только в отдельном `git worktree` под `.tmp/`.
4. Полный прогон тестов (сборка `tsdown` ≈205 с + тесты ≈88 с) выполняется **один раз и Lead'ом**, а не десятью участниками.
5. Контекст экономить: читать по якорю (`offset`/`limit`), не читать бандлы/`dist`/`lib`, тяжёлые JSON — скриптом; после большого чтения фиксировать вывод одной строкой в своём файле.
6. Всё, что не удалось проверить, — в раздел «Не проверено / открытые проверки» своего файла, с указанием, кто и как может проверить.
7. Язык документов — русский, идентификаторы/пути/команды — как в коде.
8. Участник, нашедший противоречие между своим файлом и `00-RECON.md`, сообщает Lead'у сообщением, а не переписывает бриф.

## 6. Субагенты

Каждый участник обязан использовать субагентов для сбора доказательств (правило владельца: «множество субагентов»). Порядок:

1. Разбить свою тему на 2–5 независимых вопросов-фактов (например, «какие строки в `adapter.ts` шлют актора при `claim` и `heartbeat`»).
2. Запускать субагентов пакетно (`subagent`, `run_in_background: false` для 2–3 одновременно, либо параллельно в одном сообщении).
3. В промпте субагента требовать: **вывод ≤40 строк**, обязательные `файл:строка` или команда+exit code, явный список «не проверено», и — если субагент умеет писать файлы — запись в `.work/plan-v0.3/evidence/<owner>-<NN>.md`.
4. Не отдавать субагенту решения и не просить писать план — только факты.
5. Все факты, попавшие в план, помечать источником (кто нашёл: субагент + файл/строка).
