## 2. Целевое состояние v0.3

**Стратегическая позиция (подтверждена аналитической кампанией и совпадает с ADR-позицией плана):** MyWork — authoritative work orchestration layer; DSH — runtime/session/web/platform; у Agent Teams берём паттерны (provisioning saga, advisory write intents, handoff artifacts), но не authority; coordination subsystem не строим.

**v0.3 считается достигнутым, когда одновременно верно:**

1. **Проверяемость.** Единственная команда входа восстанавливает проект с нуля (`install → typecheck ×12 → build → smoke → test → verify:profile`); ни один тест реального backend не может быть `skipped` в CI-профиле; леджеры согласованы; `done` означает прогон гейта, а не колонку.
2. **Достижимость.** Все 12 пакетов имеют runtime-точку входа через composition root; в изолированном `DSH_HOME` после smoke существует `dsh-mywork\state\controller.sqlite` ожидаемой версии схемы.
3. **Durable-состояние.** Запись состояния атомарна (temp+rename/WAL), миграции журналируются, БД имеет ограничители роста (retention + VACUUM), тела артефактов сканируются на секреты.
4. **Управляемость.** Есть бюджетный и шаговый circuit-breaker поверх `dsh-token-meter`, наружный канал `ctx.productTelemetry.emit` поверх собственного `audit`/`outbox` (**OTel не строим** — D16), runtime-инварианты, allowlist worker-поверхности (запрет `cordis_*`/dynamic-инструментов/`plugin_manager`), политика `auto-review` (реальная, а не «его нет»).
5. **Совместимость.** Манифест публикуем: `peerDependencies` по имени пакета платформы, **`>=0.1.7-rc.2 <0.3.0-0`** (актуализировано 2026-10-03, §1.4), `engines` — декларативно (читателей нет), матрица проверок; сборка клиентского бандла регистрируется платформой (панель видна в GUI после refresh).
6. **Конвейер.** MW-021…MW-026, MW-028, MW-031 закрыты: worktree-изоляция, worker от admission до результата, детерминированные verification gates, независимый review с reject-flow, интегратор, Task Setter, resident controller, recovery/stall detection.
7. **Поверхность.** Доска v0.3 (в выбранной по D02 модели), проекция с честными `degraded`/`empty`, DnD через резолвер `DropIntent → MyWorkCommand`, миграция легаси-доски с проверяемым cutover, приёмка MW-055 пройдена без «сценариев без evidence».
8. **Человек.** `HumanDecision` как durable-сущность с доставкой ответа в живую попытку, не блокирующей шаг агента; человеческая приёмка по work type (ADR028).

**Вне scope v0.3** (осознанно): координационная подсистема/mailbox, вторая authority над задачами, event sourcing TaskGraph, собственная модель/провайдер LLM, замена `AgentRuntimePort`, удаление агрегата `@linxin666/dsh-web-all`.

## 3. Принципы (нарушение = дефект плана)

1. **Платформа сначала.** Если DSH даёт шов (`token-meter`, `invariants`, `spillStore`, `deliverables`, `sandbox-policy`, `storage-domain`, `session-query`, `commands`, `systemPrompt.section`) — используем его, а не строим второй.
2. **Один authority на факт.** Статус задачи — MyWork; сессия — DSH; леджер доски — MyWork (легаси-доска после cutover — только чтение).
3. **Доказательство вместо мнения.** Гейт — команда с ожидаемым выводом; утверждение — `файл:строка` или `§`; «зелёный прогон» без проверки backend — не доказательство.
4. **Обратимость дороже скорости.** Всё, что переписывает принятые контракты или приёмки (D02), делается ADR'ом и пакетом правок, а не «по ходу».
5. **Worker не самоуправляется.** Никаких `cordis_*`, dynamic-инструментов, `plugin_manager` и самостоятельного approve в поверхности исполнителя; приёмка — не дело исполнителя.
6. **Деньги и данные — ограниченный ресурс.** Бюджет/шаги ограничены; состояние пишется атомарно; миграция без journal не начинается.
7. **Не переусердствовать.** Каждая новая сущность/сервис/шов обязана иметь потребителя в плане; «на будущее» не строим.

**Почему так:** доска (MW-047+) не имеет смысла без завершения графа (MW-025) и живого store (F-20); UI (MW-048+) не имеет смысла без backend-проекции (MW-047); приёмка (MW-055/041) — без cutover и без доказанного конвейера. Всё, что можно делать параллельно (bd/CI/леджеры/ADR/peer-контракт/UI-бандл), вынесено за критический путь.

## 6. Спор о порядке: конвейер раньше доски (D12)

| Позиция | Аргументы | Цена |
|---|---|---|
| **A. Конвейер → поверхность** (рекомендация плана) | Доска — контроллер над исполнением; без MW-021…MW-026 нажимать на доске нечего. «`done` без прогона» уже случилось (11 падений исполнений, 7 из них — на `done`-карточках). Документ внешнего анализа ставил Web/Board впереди, но сам не знал про незакрытый конвейер (§1.1(3) отчёта) | Доска появится позже; «вау-эффект» отложен |
| **B. Поверхность → конвейер** (§65 документа) | Ранняя видимость прогресса и обратная связь от пользователя; UI-каркас дешевле переделывать, пока данных мало | Доска будет показывать то, что не исполняется; риск UI поверх незрелых контрактов (K2 не решён) |
| **C. Гибрид** | Немедленно: минимальный read-only Backend проекции + панель-заглушка (этап 3, `B-20…`), полноценная доска — после конвейера | Двойная работа по панели, если D02 изменит модель зон |

**Решение плана:** A с одним исключением — **инсталлируемость** (peer-контракт + регистрация панели в GUI) делается в этапе 3, до конвейера, потому что это дёшево, снимает неизвестность платформы (`/plugins/<id>/client.js`, HMR, слоты) и не зависит от модели зон. Полноценная доска — после этапа 4.

**Условие пересмотра:** если владелец хочет видеть доску раньше (например, для демонстрации) или если этап 4 растянется больше 4 недель — переходим к C, но контракт зон (D02) обязан быть заморожен до начала UI.

### 7.2. Опровержения базы, внесённые в план (полный список — `10-DECISIONS.md` §2)

1. «9 падений на `done`» → точный ценз: **11 записей `result:failed` у 10 карточек** — `done` 7 (MW-003…MW-008, MW-043), колонка `failed` 2 (MW-001, MW-016), backlog 1 (MW-002, две записи); ни одно не является вердиктом о работе.
2. `AutonomyLevel`, названный в приёмке MW-042, **в репозитории отсутствует** (0 совпадений) — приёмка неисполнима как написана.
3. Числа MW-054 («6 done / 35 незавершённых») неверны: верно **19 и 3** (леджер rev. 324: `47b14762` = 52 карточки 32/19/1, `3fc33afb` = 3).
4. `MemoryProvider`/`SkillProvider` названы в брифе платформенными швами — **памяти в DSH нет**, `MemoryProviderPort` наш.
5. План v0.2 §5.6 «аутентификация маршрутов наследуется» — **опровергнуто**: у `WebServer` нет ни auth-хука, ни middleware (путь `register` → `handler`: `webserver/src/index.ts:166-173` и замыкание `handle` `:222-238`, вызов `route.handler(req, res)` на `:228`; переякорено 2026-10-03 — на `:319-360` лежат `match`/`applyIndexTaps`/`renderIndex`).
6. «Неатомарная запись состояния» — для SQLite **опровергнуто**: journal, транзакция на миграцию и тесты на прерывание транзакции есть (но `tests/storage-crash.test.mjs:59-93` — не тест прерывания **миграции**; уточнено верификацией); не хватает verify/backup/rollback и канонического реестра.
7. «Три леджера» противоречат сильнее, чем считалось: 55/55/41 карточки, в двух из трёх **ноль исполнений**.
8. Порядок миграций из FINAL-REPORT §10 (`lease` до `evidence`) **падает** (`invalid-input: 2 follows 4`); канон — storage v1 → evidence v2,v3 → lease v4 → planner v5 → execution v6.
9. Единый реестр миграций **нельзя** положить в `packages/storage` — `tests/boundaries.test.mjs:223-229` запрещает доменные импорты; реестр обязан жить в composition-слое.
10. **WAL уже включён и проверяется** (`sql.ts:130-138`) — «неатомарность/отсутствие WAL» неверно; реальные пробелы — `synchronous`, `auto_vacuum`, checkpoint, `VACUUM` (0 совпадений).
11. **Синтеза окна «1 000 000» в MyWork нет** (0 литералов) — P20 подтверждён иначе: реальные пробелы — пустой `listModels` и отсутствие ветки «модель не найдена».
12. **Peer-гейт DSH проверяет только `@deepseek-ai/dsh*`** (`packages/boot/app-boot/src/plugin-compatibility.ts:68,75`), объявленный MyWork `@deepseek-ai/cordis` он игнорирует — то есть гейта сейчас нет вовсе, а не «гейт молчит из-за неполного манифеста».
13. Мелкие уточнения базы: worktree не 3, а 4; P25 — не «DSH-импорт не ловится», а `scheduler`/`planner` не сканируются вовсе; P10 — `files` есть у всех 12 манифестов; `EVIDENCE_MIGRATIONS` = версии 2 и 3 (мостик не нужен), версия 7 свободна.

## 11. Механика исполнения

**Как запускается работа:** карточка берётся из `30-CARD-EDITS.md` → исполняется по шагам соответствующего файла `2N-STEPS-*.md` → гейт прогоняется буквально той командой, что написана → отчёт в `.work/reports/` → независимое review (MW-024) → только потом `done`.

**Правила исполнения:**
1. Один writer на файл/пакет; пересечение write-scope — только через Lead'а.
2. Перед первым запуском карточки: проверить `dependsOn` и наличие отчёта зависимости, а не колонку доски.
3. Любой шаг, начинающийся с «Шаг 0: подтвердить…», обязан быть подтверждён до реализации.
4. Полный прогон (build+test+smoke+verify) — на этапах и в CI, не на каждом шаге; точечные тесты — на каждом шаге.
5. Коммиты — маленькие, по шагу; сообщение в стиле репозитория; тег — только по гейту этапа.
6. Мутирующие эксперименты — только в изолированном `DSH_HOME` или отдельном `git worktree` под `.tmp/`.
7. Evidence отчёта: команда + вывод + sha коммита + изменённые пути. Без evidence карточка не закрывается.
8. Бюджет кампании: следить за расходом; при превышении лимита D05 — остановка и эскалация.

**Роли (если исполняет Agent Team):** worker (изолированный worktree) → verification gates (детерминированные команды) → reviewer (независимый агент) → integrator (слияние и завершение). Смешивать роли в одной сессии запрещено (ADR026).

## 15. Канонические правила исполнения (дополнение к §11)

Эти правила появились из проверок и обязательны для всех шагов плана.

1. **Runner.** В этом окружении `pnpm` сломан. Канонические команды: `corepack pnpm -r run <script>` (проверено: `-r` → EXIT=0, 12 пакетов) — **обязательно с `-r`**, потому что `corepack pnpm run <script>` падает за ~1 с из-за вложенного bare `pnpm` 11.7.0 из `.bin` DSH-чек-аута; точечные проверки — `node --test --test-isolation=none <файл>`, `node_modules\.bin\tsc.cmd --noEmit -p <tsconfig>`, `node <tsdown-entry>`.
